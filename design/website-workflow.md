# 游戏网站制作工作流

主线：风格探索与确认 → 完整设计、素材与规则 → 开发、验收与部署。

这份流程基于本次象棋网站的实际迭代整理。三个阶段分别解决“长什么样”“完整体验是什么”“能否按设计稳定运行”，每个阶段都有可检查的交付物。

## 下次如何启动

本流程的执行入口是个人技能 `$game-website-workflow`。说明文档用于理解流程，技能负责阶段推进、确认边界、进度恢复与完成审计。

在目标项目中，可用一句话启动：

```text
$game-website-workflow 创建持续目标：开发一个【游戏名称】网站，采用【风格】，支持【对局模式】。先让我确认风格；确认后自动完成 Pixso 设计、规则、开发和验收，并部署到项目已配置的目标。只有必要决策或缺少权限时再询问，完成后报告结果。
```

不需要上线时，将部署要求改为“完成本地开发与浏览器验收，不部署”。如果希望 AI 自主选择风格，将“先让我确认风格”改为“风格由你选择”。没有明确放弃风格确认时，仍保留开发者选风格这一环节。

持续目标需要运行环境支持。技能不会绕过权限，也不会保证配额耗尽、工具离线或应用关闭后仍持续工作；它会记录阶段、已确认选择、产物和下一动作，恢复时继续已有工作。换机器时需安装同一技能并提供所需的图像生成、Pixso 与开发工具。

已经完成技能结构与引用校验；尚未以全新游戏完整验证一次从零到上线的自动执行效果，后续按实际运行结果迭代。

## 第一阶段：生成风格图片，确认视觉方向

### 输入

- 游戏类型、面向的玩家、在线或同屏模式。
- 希望的风格、参考图片或网站、已有品牌和素材。
- 主要使用设备，以及需要保留的页面框架。

信息足够时直接形成简短设计理解；只有会改变方向的分歧才需要询问。

### 工作与产出

先生成少量有明显区别、带编号的风格方案。每个方案展示游戏本身，以及它在网页中的大致使用效果，方便比较配色、材质、字体气质、背景和信息密度。

涉及棋盘等精确操作区域时，同时展示实际游玩视角。斜视主视觉的厚度感不能自动等同于俯视棋局效果。

**交付物：**风格参考图、简短方向说明、用户选中的基准图与具体偏好。

**确认点：**用户选择或修订视觉方向。已经确认的配色与材质成为后续基准；零散的小调整不必反复重新确认整套风格。

## 第二阶段：详细网页设计，制作 Pixso 设计稿，确定规则

### 1. 补齐完整页面和关键状态

围绕选定风格生成详细网页设计，覆盖真实游玩流程：

- 大厅：创建、加入、同屏入口。
- 等待与准备：座位、邀请、开始条件。
- 对局：玩家信息、棋盘、选择与落点、棋谱、主要操作。
- 协商与异常：悔棋、求和、断线、恢复。
- 结算：胜方、关键结果、再来一局、查看棋局、返回大厅。
- 桌面、平板和手机的布局。

结算属于独立设计的游戏体验。普通确认对话框用于退出等轻量操作，不能直接替代结算画面。提示文字按必要程度安排，避免长时间占据游玩区域。

### 2. 拆出可直接使用的素材

从完整设计中形成独立素材：背景、空棋盘、透明棋子、装饰和必要图标。棋子需要保持一致的视角、尺寸、光源、边缘和阴影，并检查字形、数量及位置是否正确。

图片的裁切、透明边缘、实际显示清晰度和文件体积在这里一起检查。保留原始素材，另行生成适合网站加载的压缩版本。

**关键要求：设计稿与网页复用同一套素材。**写实木纹、雕刻和倒角应由真实图像承载；用简单圆形与文字重新拼装，会改变已经确认的视觉效果。

### 3. 用 Pixso 制作可编辑设计稿

通过 Pixso MCP 组织页面和组件：

- 图像素材保留材质，文字、按钮、布局和状态独立编辑。
- 重复棋子建立组件，每枚可操作棋子使用独立实例。
- 标注字体、色彩、间距、交互状态和动效。
- 将完整设计图与 Pixso 截图对照，检查材质、比例、层级和缺失状态。

可编辑不等于所有物体都必须重新画成矢量；整页贴图也不能替代可交付的页面结构。

### 4. 视觉细化期间并行明确规则

基础规则资料和用户定制规则分开记录，形成 `rule.md`。开发前明确：

- 棋子基本走法、阻挡和轮流操作。
- 胜负触发条件，例如将死判胜，还是实际吃掉将帅才获胜。
- 是否允许送将、不解将等休闲玩法。
- 悔棋、和棋、主动结束、退出、断线及再来一局的处理。
- 哪些情况只是提示，哪些情况需要禁止操作或结束对局。

设计中的状态与规则保持对应，防止界面承诺一种玩法、代码执行另一种玩法。

**交付物：**完整页面设计、可编辑 Pixso 稿、素材包、视觉规范、`rule.md`。

**确认点：**确认完整视觉、操作方式及主要规则分歧。若用户已经明确授权按现有方案继续，直接推进，不重复索要相同确认。

## 第三阶段：按设计和规则开发，验收后部署

### 1. 先完成一个可检查的完整对局

优先打通进入游戏、操作、结束、结算和再开一局。页面使用设计阶段的素材与组件规范，规则依据 `rule.md` 实现。

在线与同屏尽量共享规则。在线结果由服务器确认，界面负责反馈与动画；动作完成、断线恢复和重复消息不能让棋局状态发生分歧。

### 2. 按真实交互完善体验

合法动作有适量动画，错误反馈短暂且明确。系统减少动态效果时仍能理解操作结果。鼠标、触控、不同屏幕尺寸分别检查。

结算、悔棋协商、重连等关键状态用真实操作触发验收，不能只检查静态样图。

### 3. 同时检查视觉还原与加载体验

- 将真实网页截图与设计稿并排比较，检查材质、尺寸、间距和页面完整性。
- 检查首次加载、再次进入、弱网、图片缺失和过时缓存。
- 素材按实际显示需求压缩；需要时提前加载和解码，避免进入棋局后逐枚出现。
- 静态资源缓存与版本更新配套设计，避免用户继续运行旧样式或旧规则。

### 4. 完成测试与发布

针对走法、胜负、协商、同步和恢复运行适当测试，再用真实浏览器验证完整流程。浏览器的手机模拟与实体设备验收分别记录。

发布在用户明确授权后执行；已有授权无需重复申请。发布前检查变更和交付文件中的个人环境信息，构建只包含运行所需文件。保留回滚版本与房间存档，发布后核对线上产物并重复关键操作。

**交付物：**可运行网站、必要测试、验收结果、部署产物和简短维护说明。

**完成标准：**视觉与已确认设计一致，规则与用户约定一致，关键流程能够运行，加载体验经过检查；如果要求上线，公网验证也必须完成。

## 本次案例对流程的补充

| 实际问题 | 对应的流程改进 |
| --- | --- |
| 概念图棋子写实，初版 Pixso 棋子过于简单 | 素材拆解后直接建立图像组件，设计与代码复用同一资产 |
| 斜视参考图与俯视棋局的厚度感不同 | 风格阶段就展示实际游玩视角 |
| 网站进入时有明显图片加载过程 | 素材阶段控制体积，开发阶段验收首次加载与缓存 |
| 强制解将不符合期望玩法 | 在开发前区分基础走法和用户定制规则 |
| 将死自动结算与实际吃将判胜不一致 | 将胜负触发条件写进规则和测试 |
| 通用长条弹窗缺少游戏结算感 | 详细设计阶段单独设计结算页及后续操作 |

本次运行图片从约 2.05 MB 压缩至 382 KB，减少约 81.4%；这是本次素材的实际结果，不作为所有项目必须达到的固定比例。
